# Public STUN Accelerates; Only Relays Guarantee

In October 2026 Undepressable can still rely on public STUN, but on a smaller and more country-dependent set than its current four defaults: **`stun.cloudflare.com:3478`** (documented "free and unlimited", though no censorship measurement covers it), **`stun.l.google.com:19302`** (fine from China, Turkey and, since September, Iran, but failing **60–95% of the time from Russia every month since November 2025**), and a few hourly-validated port-3478 hosts that Tor vetted for Snowflake in April 2026 (**`stun.telnyx.com`, `stun.epygi.com`, `stun.m-online.net`**), which fail **≤2% from Russia, Iran and China**. Two current defaults should go: `stun.nextcloud.com:443`, because Russia and Iran now drop unidentified UDP on port 443 (**95–100% failure since mid-2026 while the same host on 3478 keeps answering**), and `stun1.l.google.com`, which shares Google's address with `stun.l.google.com` and adds no redundancy. The deeper finding is that STUN is only an accelerant: ICE connectivity checks are themselves STUN transactions, so the alternatives that genuinely remove the public-server dependency are global IPv6 on both ends (no server at all; ~53% of random German pairs, ~2% of Icelandic ones), a TURN-over-UDP relay the app already trusts (libwebrtc uses every UDP TURN server as a STUN server and every Allocate response carries the mapped address), and relay-only `turns:443` (no STUN, no UDP). Every browser-side trick that avoids servers altogether — address echo over WebSocket, birthday-paradox port guessing, `stuns:` — either cannot be performed from a web page or does not solve the case that failed in the field: two endpoint-dependent NATs (a VPN exit and a mobile carrier) without IPv6, which no STUN list fixes and only a relay crosses. The published site therefore needs a relay it can name with public, quota-capped credentials — a **€4–5/month VPS running coturn with `turns:` on 443**, or Metered's front-end-safe credential link — and should treat **Cloudflare's 1,000 GB/month free TURN** as the best deal only if the project accepts one tiny credential-minting Worker.

## Only a handful of public STUN hosts pass both the hourly checker and the censorship data

There is exactly one continuously validated public STUN list in 2026. pradt2/always-online-stun runs a Rust checker on GitHub Actions that sends an RFC 5389 Binding request hourly over UDP and TCP, IPv4 and IPv6, and commits shuffled `valid_*` files; on 2026-10-13 `valid_hosts.txt` held **257 UDP entries, 251 of them on port 3478**, five on Google's 19302 and a single one on 443 (`stun.nextcloud.com:443`), while the TCP list held 88 and no TLS list exists at all ([valid_hosts.txt](https://raw.githubusercontent.com/pradt2/always-online-stun/master/valid_hosts.txt); [valid_hosts_tcp.txt](https://raw.githubusercontent.com/pradt2/always-online-stun/master/valid_hosts_tcp.txt); [README](https://raw.githubusercontent.com/pradt2/always-online-stun/master/README.md)). The checker proves liveness, not NAT-discovery capability: its own README says "no actual verification of the NAT behaviour testing capabilities is carried out" ([README](https://raw.githubusercontent.com/pradt2/always-online-stun/master/README.md)). Notably, `stun.cloudflare.com` does not appear in its `candidates.txt` at all, so "the hourly checker says Cloudflare is up" can never be claimed; Cloudflare's status rests on its own documentation, which states "Cloudflare's STUN service at `stun.cloudflare.com` is free and unlimited" on 3478/udp, with 53/udp listed as an alternate on one allowlist page ([candidates.txt](https://raw.githubusercontent.com/pradt2/always-online-stun/master/candidates.txt); [Cloudflare TURN FAQ](https://github.com/cloudflare/cloudflare-docs/blob/production/src/content/docs/realtime/turn/faq.mdx); [network allowlist](https://github.com/cloudflare/cloudflare-docs/blob/production/src/content/docs/realtime/realtimekit/network-allowlist.mdx)). Google publishes no terms, SLA or rate limits for `stun.l.google.com`; its Meet network page documents UDP 19302–19309 and the 74.125.250.0/24 range without ever naming the STUN host ([Google Meet network page](https://knowledge.workspace.google.com/admin/meet/prepare-your-network-for-meet-meetings-and-live-streams)). Twilio is the only other operator with written terms ("unlimited highly reliable STUN lookups for free") ([Twilio](https://www.twilio.com/en-us/stun-turn)).

The second authority is Tor, which hand-validates Snowflake's default list for RFC 5780 NAT-type discovery and rotates it under blocking. The list served live by rdsys on 2026-10-13 is `stun.epygi.com`, `stun.uls.co.za`, `stun.voipgate.com`, `stun.mixvoip.com`, `stun.telnyx.com`, `stun.hot-chilli.net`, `stun.fitauto.ru` and `stun.m-online.net`, all on 3478 ([bridges.torproject.org](https://bridges.torproject.org/moat/circumvention/builtin)). The April 2026 change that produced it added telnyx, hot-chilli, fitauto and m-online as "tested and validated servers" and removed **`stun.nextcloud.com:3478`, `stun.bethesda.net` and `stun.nextcloud.com:443`** as servers "that don't correctly support NAT Type discovery" ([tor-browser-build #41775](https://gitlab.torproject.org/api/v4/projects/tpo%2Fapplications%2Ftor-browser-build/issues/41775); [MR !1462](https://gitlab.torproject.org/tpo/applications/tor-browser-build/-/merge_requests/1462)). Google's `stun.l.google.com:19302` had already been dropped in December 2024 as "online, but doesn't support NAT discovery" ([MR !1115](https://gitlab.torproject.org/tpo/applications/tor-browser-build/-/merge_requests/1115)). Snowflake's rules are explicit: "These must be STUN (over UDP) servers … We recommend using servers that have implemented NAT discovery" ([Snowflake client README](https://gitlab.torproject.org/tpo/anti-censorship/pluggable-transports/snowflake/-/raw/main/client/README.md)). That requirement matters for Undepressable's NAT probe, which compares the ports two STUN servers report; a server without RFC 5780 still answers Binding, so the probe works, but Tor's list is the only public vetting of which servers behave well under load and over time.

The third source is OONI's `stunreachability` test, which counts a measurement as failed when no valid Binding response arrives ([OONI spec](https://raw.githubusercontent.com/ooni/spec/master/nettests/ts-025-stun-reachability.md)). It covers only the 21 hosts Snowflake has ever shipped — not Cloudflare, Twilio or Metered — and its probes are volunteer-run, so a Chinese figure may come from behind a VPN. Within those limits the data is decisive. From Russia, **`stun.l.google.com:19302` has been anomalous 81%, 92%, 92%, 29%, 96%, 82%, 87%, 64%, 67%, 51%, 62% and 76% of the time in each month from November 2025 to October 2026**, after 0–14% through most of 2025 ([OONI RU, monthly, Google](https://api.ooni.io/api/v1/aggregation?test_name=stunreachability&probe_cc=RU&since=2025-01-01&until=2026-10-13&time_grain=month&axis_x=measurement_start_day&input=stun://stun.l.google.com:19302)). **`stun.nextcloud.com:443` jumped from 13–14% to 98% anomalous in July 2026 and has stayed at 95–97%**, while the same host on 3478 sat at 2–11% in the same months ([OONI RU, nextcloud:443](https://api.ooni.io/api/v1/aggregation?test_name=stunreachability&probe_cc=RU&since=2025-01-01&until=2026-10-13&time_grain=month&axis_x=measurement_start_day&input=stun://stun.nextcloud.com:443); [nextcloud:3478](https://api.ooni.io/api/v1/aggregation?test_name=stunreachability&probe_cc=RU&since=2025-01-01&until=2026-10-13&time_grain=month&axis_x=measurement_start_day&input=stun://stun.nextcloud.com:3478)). Even in Germany and the United States `stun.nextcloud.com:443` fails 14.4% and 5.5% of the time versus 3.5% and 2.8% on 3478 ([OONI DE](https://api.ooni.io/api/v1/aggregation?test_name=stunreachability&probe_cc=DE&since=2026-04-01&until=2026-10-13&axis_x=input); [OONI US](https://api.ooni.io/api/v1/aggregation?test_name=stunreachability&probe_cc=US&since=2026-04-01&until=2026-10-13&axis_x=input)).

Two hosts on Tor's own list contribute nothing to Russian or Chinese users: `stun.voipgate.com` and `stun.mixvoip.com` fail **98.7% from Russia and ~98% from China** in every month since early 2025 while passing at 2–4% from Germany, the US, Iran and Turkey, a signature of operator-side geoblocking rather than censorship ([OONI RU](https://api.ooni.io/api/v1/aggregation?test_name=stunreachability&probe_cc=RU&since=2026-04-01&until=2026-10-13&axis_x=input); [OONI CN](https://api.ooni.io/api/v1/aggregation?test_name=stunreachability&probe_cc=CN&since=2026-04-01&until=2026-10-13&axis_x=input)); Tor's own ticket from March 2026 confirms the reports ([snowflake#40523](https://gitlab.torproject.org/tpo/anti-censorship/pluggable-transports/snowflake/-/issues/40523)). Finally, the port-443 and TLS escape hatches do not exist for a `stun:` entry. In libwebrtc's parser `stuns:` falls through to the same `stun_servers->insert(...)` as `stun:` with no TLS and default port 3478; Firefox throws `NotSupportedError` ("stuns scheme is not supported"); WebKit only checks the scheme string and hands the URL to libwebrtc ([ice_server_parsing.cc](https://webrtc.googlesource.com/src/+/refs/heads/main/pc/ice_server_parsing.cc); [Firefox IceServerParser.cpp](https://github.com/mozilla-firefox/firefox/blob/main/dom/media/webrtc/common/IceServerParser.cpp); [w3c/webrtc-pc #2270](https://github.com/w3c/webrtc-pc/issues/2270)). So the 88-host TCP list is irrelevant to a browser, and a network that blocks UDP needs TURN over TCP/TLS, not a different STUN URL.

## Browsers can drop public STUN in four ways, and three of them need a server you control

The framing fact is that ICE connectivity checks *are* STUN Binding transactions sent peer to peer; a STUN *server* is only needed to learn one's own mapped address before checks start, and once any check reaches the peer, the peer's Binding response reveals the mapped address as a peer-reflexive candidate ([RFC 8445 §2.2](https://www.rfc-editor.org/rfc/rfc8445.html)). Everything below follows from that.

The one path that is both STUN-free and server-free is **global IPv6 on both ends**. With no `iceServers` at all, browsers still gather host candidates and connect when the peer is directly reachable; libwebrtc fixed exactly this case in 2015 ("even without STUN/TURN, as long as the peer is on the open internet, the connectivity should work") ([webrtc commit 1147702](https://webrtc.googlesource.com/src/+/1147702958b7639eda2f7fe072103b95be59e5c0); [MDN](https://developer.mozilla.org/en-US/docs/Web/API/RTCPeerConnection/RTCPeerConnection)). A global IPv6 host candidate already is the public address, so a server-reflexive candidate would be redundant by RFC 8445's own rule, and the ICE checks themselves open the stateful-firewall pinholes in both directions. libwebrtc sorts networks by RFC 3484-bis precedence and gives global IPv6 a value of 40 against 30 for IPv4, so Chromium, Edge and Safari try IPv6 host pairs first ([ip_address.cc](https://chromium.googlesource.com/external/webrtc/+/refs/heads/main/rtc_base/ip_address.cc); [network.cc](https://chromium.googlesource.com/external/webrtc/+/refs/heads/main/rtc_base/network.cc)); RFC 8421 asks implementations to intermingle families Happy-Eyeballs-style so a broken IPv6 path costs setup time rather than failure ([RFC 8421](https://www.rfc-editor.org/rfc/rfc8421.html)). The constraint is deployment: APNIC measures **Germany at 72.9% IPv6-capable but Iceland at only 13.0%** (30-day smoothed figures, last record dated 2026-10-10), which makes roughly 53% of random German pairs and about 2% of Icelandic pairs dual-IPv6 ([APNIC DE](https://data1.labs.apnic.net/v6stats/v6economy/DE.json); [APNIC IS](https://data1.labs.apnic.net/v6stats/v6economy/IS.json)). Tailscale's verdict stands: in an all-IPv6 world "we can get rid of STUN, the birthday paradox trick, port mapping protocols," but on-device firewalls remain, so simultaneous send, a signaling channel and a fallback relay are still needed ([Tailscale](https://tailscale.com/blog/how-nat-traversal-works)).

The path that removes *public* STUN while keeping direct connections is **the app's own TURN relay doubling as its STUN server**, and it works by two independent mechanisms. By protocol, every TURN Allocate success response carries XOR-MAPPED-ADDRESS, the client's mapped address, so an ICE agent gets its server-reflexive candidate from the allocation itself ([RFC 8656 §7.2](https://www.rfc-editor.org/rfc/rfc8656.html); [RFC 8445 §5.1.1.2](https://www.rfc-editor.org/rfc/rfc8445.html)). By implementation, libwebrtc's port allocator states "Every UDP TURN server should also be used as a STUN server if use_turn_server_as_stun_server is not disabled or the stun servers are empty," calls `GetRelayServerAddresses(PROTO_UDP)` and inserts those addresses into the STUN list; this is on by default ([basic_port_allocator.cc](https://chromium.googlesource.com/external/webrtc/+/refs/heads/main/p2p/client/basic_port_allocator.cc)). Firefox's stack reaches the same end differently: "creating a relay candidate also creates a srflx candidate that piggybacks on the TURN requests" ([Mozilla bug 1208096](https://bugzilla.mozilla.org/show_bug.cgi?id=1208096)). On the server side coturn allows anonymous Binding by default, and eturnal serves STUN and TURN on 3478 UDP/TCP out of the box ([coturn README](https://github.com/coturn/coturn/blob/master/README.turnserver); [eturnal docs](https://eturnal.net/doc/)). Two caveats bound this. Only **UDP** TURN entries count: `turns:` and `?transport=tcp` entries are never added as STUN servers, so a `turns:443`-only configuration yields no server-reflexive candidates at all ([basic_port_allocator.cc](https://chromium.googlesource.com/external/webrtc/+/refs/heads/main/p2p/client/basic_port_allocator.cc)). And whether Cloudflare's `turn.cloudflare.com` answers bare Binding requests is undocumented — Cloudflare lists STUN only under `stun.cloudflare.com` ([Cloudflare TURN docs](https://developers.cloudflare.com/realtime/turn/)) — so a hosted relay must be tested in `chrome://webrtc-internals` before the app drops its public STUN list in its favour.

The third path is **peer-reflexive discovery**: if one side is reachable — public IP, global IPv6, or an endpoint-independent NAT whose mapped address was learned somehow — the other side's checks toward it open a fresh mapping that the reachable side learns as a prflx candidate, so one symmetric NAT in the pair is survivable; two are not ([RFC 8445 §2.2](https://www.rfc-editor.org/rfc/rfc8445.html); [Tailscale](https://tailscale.com/blog/how-nat-traversal-works)). This is also why RFC 6888 matters to this app: a compliant carrier-grade NAT "MUST" have endpoint-independent mapping and is recommended to use endpoint-independent filtering precisely because "some games and peer-to-peer applications require EIF for the NAT traversal to work" ([RFC 6888](https://www.rfc-editor.org/rfc/rfc6888.html)). A German mobile SIM is therefore often the *easy* side, provided it can learn its mapped address from somewhere — which brings the problem straight back to needing one STUN-capable server the app can reach.

The fourth path is **relay-only over `turns:443`**, which is the one configuration that needs no STUN of any kind, sends no UDP from the client, crosses symmetric NAT and UDP-blocked networks alike, and presents to an observer as a TLS session to port 443. With `iceTransportPolicy: "relay"` only relayed candidates are considered ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/RTCPeerConnection/RTCPeerConnection)), and Cloudflare offers TURN over TLS on 5349 with 443 as an alternate, TURN over TCP on 3478/80 and TURN over UDP on 3478/443 ([Cloudflare TURN docs](https://developers.cloudflare.com/realtime/turn/)). The price is that every byte crosses the operator's relay in both directions, plus one extra round trip, plus TCP head-of-line blocking under loss. Tailscale's DERP shows the same trade: relays "blindly forward already-encrypted traffic," run over HTTPS "which is handy on networks with strict outbound rules," and are "a last resort" — yet even DERP ships a STUN listener on UDP 3478 for its own clients ([Tailscale DERP](https://tailscale.com/kb/1232/derp-servers); [Tailscale firewall ports](https://tailscale.com/kb/1082/firewall-ports)). Relay-only removes the need for STUN; it does not remove the need for a server someone operates.

A fifth option, **a self-hosted STUN-only responder**, is almost free in resources — coturn's `--stun-only` mode, eturnal, or Tailscale's `derper` binary need one public IPv4 with UDP 3478 open and reply from the same port ([coturn README](https://github.com/coturn/coturn/blob/master/README.turnserver); [derper](https://github.com/tailscale/tailscale/blob/main/cmd/derper/derper.go)) — and it can share a VPS with a Nostr relay on 443/WSS without a port conflict. Its value over "TURN as STUN" is only that clients get their mapped address without TURN credentials, and its weakness is that a single IP is trivially blockable, which is exactly why Snowflake refuses to run its own: "a censor would experience no collateral harm in blocking them" ([Bocovich et al., USENIX Security 2024](https://www.usenix.org/system/files/usenixsecurity24-bocovich.pdf)). Cloudflare Workers cannot host it: Workers have no UDP sockets and no inbound TCP listeners ([Workers TCP sockets](https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/)).

What does *not* work from a browser deserves equal clarity. A signaling server can echo the client's public IP but never its NAT-mapped UDP port, because NAT mappings are keyed per internal (IP, port, transport) tuple and the query must come from the socket that will carry media ([RFC 4787](https://www.rfc-editor.org/rfc/rfc4787.html); [Tailscale](https://tailscale.com/blog/how-nat-traversal-works)); the echoed IP is useful for IPv6 detection and relay selection, not as a candidate. Birthday-paradox punching needs ~256 sockets on the hard side and random probing from the easy side, reaching 50% after 174 probes and 99.9% after 2,048 — but with two hard NATs the chance after 20 seconds is 0.01% and 99.9% needs ~170,000 probes per side ([Tailscale](https://tailscale.com/blog/how-nat-traversal-works)); a web page cannot choose source ports, open hundreds of sockets, send bare UDP or read ICMP, and raw sockets exist only in Chromium's Isolated-Web-App Direct Sockets ([Chrome IWA](https://developer.chrome.com/docs/iwa/direct-sockets)). libp2p's DCUtR replaces STUN with observed addresses from a peer you already talk to, but even with that machinery and native code it succeeds **70% ± 7% overall and 39.7% behind symmetric NAT**, and 36% of NAT'd peers never obtain a relay reservation to start from ([ProbeLab](https://probelab.io/blog/can-libp2p-punch-through-nats/)). No 2024–2026 standard changes this: WebTransport is client-server only, RTP-over-QUIC is an expired Experimental draft, and mDNS candidate obfuscation makes IPv4 host candidates *less* useful across networks, not more ([W3C WebTransport charter](https://www.w3.org/groups/wg/webtransport/charters/active/); [RoQ draft](https://datatracker.ietf.org/doc/html/draft-ietf-avtcore-rtp-over-quic-14); [mDNS ICE draft](https://datatracker.ietf.org/doc/draft-ietf-mmusic-mdns-ice-candidates/)).

| Path | Requires | Solves | Does not solve |
|---|---|---|---|
| Global IPv6 on both ends | both peers with global IPv6, outbound UDP, signaling | direct connection with no STUN and no TURN; bypasses CGNAT'd IPv4 | Iceland (13%) and most VPN exits; outbound-UDP blocks; still ~half of German pairs |
| TURN-over-UDP as STUN | one `turn:host:3478?transport=udp` entry with credentials | mapped address from the app's own server; public STUN list can be empty | UDP-blocked networks; `turns:`/TCP entries do not count; Cloudflare's TURN host untested for Binding |
| Peer-reflexive discovery | one side reachable and aware of its address | the other side may be symmetric | both symmetric; neither side knows its address |
| Relay-only `turns:443` | TURN with a TLS certificate on 443, credentials | both symmetric, UDP blocked, STUN/DTLS DPI; no STUN, no UDP | all media crosses the relay (cost, latency, TCP loss behaviour); relay is one blockable point |
| Self-hosted STUN-only | VPS with public IPv4, UDP 3478 | mapped address without TURN credentials; co-locates with a Nostr relay | still a server; single IP easily blocked; RFC 5780 needs two addresses |
| Address echo over WSS | nothing beyond signaling | public IP for NAT hints, IPv6 detection, relay choice | the UDP port mapping; cannot produce a usable candidate |
| Port prediction / birthday / pwnat | raw sockets, ICMP | — | impossible from a web page; fails with two hard NATs anyway |
| `stuns:` / STUN over TCP | — | nothing | Chromium silently downgrades to UDP 3478; Firefox rejects; TCP mapping is useless for UDP media |

## The Iceland–Germany failure was a relay problem that no STUN list could fix

The field test paired a VPN exit in Iceland with a German mobile carrier, and the two could not connect. The research cannot say which of the failure classes applied — nobody captured candidates — but every class that fits is relay-only. VPN exits are the canonical "hard" side: Tailscale's taxonomy puts symmetric NAT and CGNAT among the networks that end up on relays, and "it only takes one of them in the whole path to break our current traversal plans" ([Tailscale](https://tailscale.com/blog/how-nat-traversal-works); [SCALE 23X slides](https://www.socallinuxexpo.org/sites/default/files/2026-03/Kevin-SCALE-23X-Slides.pdf)). If the German side's CGNAT is RFC 6888-compliant (endpoint-independent mapping), the pair was traversable *provided the mobile side learned its mapped address* — from STUN or from a TURN allocation — and the VPN side's checks then opened a fresh mapping that the mobile side could learn as peer-reflexive. If the mobile side's STUN requests never got answers (a carrier or VPN dropping UDP to 19302 or 443, or a UDP-hostile VPN client), or if the carrier NAT is itself endpoint-dependent, the pair was two hard NATs, where RFC 8656 says "hole punching techniques generally fail" and "it is necessary to use the services of an intermediate host that acts as a relay" ([RFC 8656 §1](https://www.rfc-editor.org/rfc/rfc8656.html)). IPv6 could not rescue it: Iceland's 13% capability makes a VPN exit there very unlikely to offer a global IPv6 host candidate ([APNIC IS](https://data1.labs.apnic.net/v6stats/v6economy/IS.json)). The one actionable lesson is that a better STUN list would at most have helped the German side classify itself; it could never have made the Icelandic exit reachable.

How often a relay is needed in general is industry lore rather than measurement, but the range is stable: BlogGeek's "around 80% of all connections can be resolved by either using the local IP address or by use of STUN," vendor figures of 15–25% relayed for consumer traffic rising to 40–60% on locked-down enterprise networks, and Chrome usage metrics cited second-hand by a TURN vendor at "one in five" ([BlogGeek](https://bloggeek.me/webrtc-turn/); [Fora Soft](https://www.forasoft.com/learn/video-streaming/articles-streaming/turn-bandwidth-calculator); [Metered](https://www.metered.ca/blog/what-is-a-turn-server/)). Nobody quantifies the figure for censored networks, where UDP throttling and STUN DNS blocking push it higher. Russia is the clearest case that relays are the only answer: its 2025 call blocking is attributed by the zapret community to DPI keyed on the STUN layer-7 signature itself (users bypass it with `--filter-l7=stun --dpi-desync=fake`, which must run on both ends), and since 30 March 2026 the censor has also fingerprinted the DTLS ClientHello of Snowflake connections, cutting Russian success to about 50–60% against near 100% for Iranian clients ([zapret #1668](https://github.com/bol-van/zapret/discussions/1668); [net4people #603](https://github.com/net4people/bbs/issues/603)). Neither a different STUN host nor a different port helps against a filter that matches the 0x2112A442 magic cookie every Binding request carries ([RFC 8489 §5](https://www.rfc-editor.org/rfc/rfc8489.html#section-5)); only a relay over TLS, which carries no STUN or DTLS in the clear, does — which is exactly what the app's blend-in mode already is.

Every comparable production service has reached the same conclusion and runs its own relay with a port-443 escape hatch, keeping public STUN at most as a development default. Jitsi's open-source default STUN is a Jitsi-run host on port 443 and its handbook calls a TURN listener on 443 "useful" because "a direct connection is not always possible" ([jitsi-meet config.js](https://github.com/jitsi/jitsi-meet/blob/master/config.js); [Jitsi handbook](https://jitsi.github.io/handbook/docs/devops-guide/turn/)). Signal mints Cloudflare TURN credentials server-side and advertises `turn:%s:80?transport=tcp` next to Cloudflare's 443 endpoints ([Signal-Server sample.yml](https://github.com/signalapp/Signal-Server/blob/main/service/config/sample.yml)). Matrix's reference client falls back to `stun:turn.matrix.org` only when the operator opts in, with the flag defaulting to `false` to avoid leaking call metadata ([matrix-js-sdk call.ts](https://github.com/matrix-org/matrix-js-sdk/blob/develop/src/webrtc/call.ts)). Tailscale starts every connection on DERP over HTTPS and upgrades to direct "usually within a few seconds," so the relay is the first path rather than the last ([Tailscale](https://tailscale.com/blog/how-nat-traversal-works)). Snowflake is the lone project that uses public STUN only, and it can afford to because it matches clients to *any* proxy by self-assessed NAT type rather than connecting a particular pair — "a fallback to TURN would be problematic for Snowflake, because the TURN servers themselves would become targets of blocking" ([Bocovich et al.](https://www.usenix.org/system/files/usenixsecurity24-bocovich.pdf)). Undepressable must connect a particular filmer to particular viewers, so Snowflake's trick is unavailable and the mainstream pattern applies. The browser-library ecosystem meanwhile shows what the app inherits by default: Trystero ships `stun.l.google.com`, `stun1`, `stun2` and `stun.cloudflare.com`, PeerJS, simple-peer, Snapdrop and PairDrop all default to Google, and only PeerJS ships a TURN server at all (with shared public credentials) ([Trystero peer.mjs](https://cdn.jsdelivr.net/npm/@trystero-p2p/core/dist/peer.mjs); [js-libp2p constants](https://github.com/libp2p/js-libp2p/blob/main/packages/transport-webrtc/src/constants.ts); [PeerJS util.ts](https://github.com/peers/peerjs/blob/master/lib/util.ts)). A censor that blocks Google STUN breaks the default path of every one of these at once, which is the collateral-damage calculus Russia has evidently accepted.

## A static site can only publish capped credentials, so choose the relay by its cap and its port 443

Anything a GitHub Pages site can use is public by construction. The TURN REST API scheme (username `timestamp:userid`, password `base64(HMAC-SHA1(secret, username))`) was designed so that access can be controlled "even if the credentials can be discovered by the user," but minting requires the secret, which cannot live in a static site ([draft-uberti-behave-turn-rest](https://datatracker.ietf.org/doc/html/draft-uberti-behave-turn-rest); [coturn turnserver.conf](https://raw.githubusercontent.com/coturn/coturn/master/examples/etc/turnserver.conf)). The best any provider offers is Metered's framing — "If someone stole your TURN Credential they cannot do anything other than use up your TURN Server quota" — plus revocation and quota-triggered auto-disable ([Metered expiring credentials](https://metered.ca/docs/turnserver-guides/expiring-turn-credentials)). No provider was found that binds TURN credentials to an origin; Cloudflare's own speedtest Worker checks the `Referer` against an allowlist, which a forged header defeats ([Cloudflare speedtest TURN worker](https://mintlify.wiki/cloudflare/speedtest/packet-loss/turn-server-setup)). The era of shared public relays is also over: the Open Relay Project's `openrelayproject`/`openrelayproject` credentials of 2022 gave way to a mandatory free account "to prevent abuse" by 2023, Cloudflare says "The public Cloudflare TURN server is deprecated and will be discontinued," Subspace shut down in May 2022, and **neither `freestun.net` nor `relay.backups.cz` — the two entries in the app's `PUBLIC_RELAY_CANDIDATES` — could be verified at all** (freestun.net sits behind a Cloudflare JavaScript challenge; backups.cz returns nothing in search) ([Dev.to free list](https://dev.to/aprogrammer22/list-of-free-stun-and-turn-servers-open-relay-project-3a70); [Cloudflare speedtest TURN worker](https://mintlify.wiki/cloudflare/speedtest/packet-loss/turn-server-setup); [WebRTC.ventures on Subspace](https://webrtc.ventures/2022/05/webrtclive-subspace/)). The only living shared pool is Open Relay's `staticauth.openrelay.metered.ca` with the published secret `openrelayprojectsecret` on ports 80 and 443 — a 20 GB/month pool anyone can mint against ([Metered Open Relay](https://www.metered.ca/tools/openrelay/)).

Among hosted providers, four are realistic and they differ mainly in whether the static site can use them unaided. **Cloudflare Realtime TURN** gives 1,000 GB/month free egress, then $0.05/GB, ingress free, with `turns:turn.cloudflare.com:443?transport=tcp` and `turn:turn.cloudflare.com:443?transport=udp` documented, anycast across hundreds of locations, per-client throttling above roughly 50–100 Mbps, and no presence in China ([Cloudflare pricing](https://developers.cloudflare.com/realtime/pricing/); [Cloudflare TURN FAQ](https://developers.cloudflare.com/realtime/turn/faq/); [generate credentials](https://developers.cloudflare.com/realtime/turn/generate-credentials/)). But credentials are short-lived only (48-hour maximum), minted by POSTing to Cloudflare's API with a bearer token that "should be kept on the server side," so a static site needs a backend; Cloudflare's own example is a Worker holding the token as a secret, exposing `/turn-credentials` with a 240-second TTL, which fits in the Workers free tier of 100,000 requests per day ([generate credentials](https://developers.cloudflare.com/realtime/turn/generate-credentials/); [speedtest TURN worker](https://mintlify.wiki/cloudflare/speedtest/packet-loss/turn-server-setup); [Workers pricing](https://workers.cloudflare.com/pricing/)). The FOCI 2025 argument for commercial anycast TURN as circumvention infrastructure — blocking Cloudflare's TURN IPs would cause collateral damage to ordinary WebRTC — is a hypothesis, not a tested result, but it is the strongest censorship-resistance case for any hosted option ([FOCI 2025](https://petsymposium.org/foci/2025/foci-2025-0003.php)). **Metered** is the hosted provider whose documented model fits a static site: its per-credential "Credential API Key" "can be used in the front-end as well, as it is credential scoped," its credentials link `https://<app>.metered.live/api/v1/turn/credentials?apiKey=…` returns an `iceServers` array nearest to the user, `turns:global.relay.metered.ca:443?transport=tcp` is published, and quotas can auto-disable credentials at 100% with webhooks at 80% ([Metered TURN REST API](https://www.metered.ca/docs/turn-rest-api/); [creating credentials](https://www.metered.ca/docs/turn-server-service/creating-turn-credentials/); [Metered STUN/TURN](https://www.metered.ca/stun-turn)). Its free allowance is genuinely ambiguous — 500 MB trial, 20 GB Open Relay, or 50 GB "Free Plan" on undated pages — and Metered meters ingress plus egress, so the dashboard quota must be read before relying on it; paid starts at $99/month for 150 GB ([Metered STUN/TURN](https://www.metered.ca/stun-turn); [Metered Open Relay](https://www.metered.ca/tools/openrelay/)). **ExpressTURN** gives 1,000 GB/month free with static long-term credentials but the free plan "supports TCP and UDP on port 3478" only; $9/month unlocks TURNS, all 18 locations and 5,000 GB ([ExpressTURN](https://www.expressturn.com/)). **Xirsys** hard-stops at 500 MB/month free and starts at $39/month for 50 GB with static credentials, TLS/443 undocumented ([Xirsys pricing](https://xirsys.com/pricing/)). **Twilio** is the expensive backend-only reference at $0.40/GB in Germany and the US, with TCP on 443 but no `turns:` URI documented ([Twilio pricing](https://www.twilio.com/en-us/stun-turn/pricing); [Twilio API](https://www.twilio.com/docs/stun-turn/api)).

Self-hosting is cheaper than any of these at modest volume because cost is dominated by the fixed VPS fee. Hetzner bills outgoing traffic only, includes 20 TB/month on EU cloud servers and charges about €1/TB beyond; its smallest plan moved to €3.99/month in April 2026 ([Hetzner billing FAQ](https://docs.hetzner.com/cloud/billing/faq); [egresscost.com](https://egresscost.com/hetzner); [Kuberns on Hetzner pricing](https://kuberns.com/blogs/hetzner-cloud-pricing/)). OVHcloud's VPS-1 starts at $4.54/month with "unlimited traffic" at 500 Mbps, Scaleway's STARDUST1-S costs about €0.43/month but caps at 100 Mbps, and Oracle's Always Free tier offers 10 TB/month egress on Arm VMs that are widely reported as hard to obtain ([OVHcloud VPS](https://www.ovhcloud.com/en/vps/); [Scaleway pricing](https://www.scaleway.com/en/pricing/virtual-instances/); [Oracle free tier](https://oracle.com/at/cloud/free)). The recipe that survives public credentials is coturn with `lt-cred-mech` and one `user=` entry, `tls-listening-port=443` (via `setcap` or an nginx `stream` block with `ssl_preread` routing by SNI, with coturn holding the certificate because TLS is not terminated upstream), `no-tcp-relay`, `denied-peer-ip` for private ranges plus `no-multicast-peers`, `user-quota` and `total-quota` sized to expected sessions (Synapse's reference is 12 per user and 1,200 total), `max-bps` at roughly 1.5× the stream bitrate and `bps-capacity` just under the uplink ([coturn turnserver.conf](https://raw.githubusercontent.com/coturn/coturn/master/examples/etc/turnserver.conf); [coturn behind nginx](https://dev.to/masanori_msl/run-coturn-behind-nginx-8fc); [Nextcloud Talk coturn](https://nextcloud-talk.readthedocs.io/en/latest/coturn/); [Synapse TURN how-to](https://github.com/matrix-org/synapse/blob/erikj/state_delta_writeup/docs/turn-howto.rst)). eturnal does the same with fewer knobs (`max_bps`, `max_permissions`, a default peer blacklist), with the caveat that its `max_bps` applies only to TCP and TLS ([eturnal docs](https://eturnal.net/doc/)). The trade-off against Cloudflare is blockability: a single-IP VPS offers a censor no collateral damage, which is the FOCI paper's reason to prefer commercial anycast in hostile countries ([FOCI 2025](https://petsymposium.org/foci/2025/foci-2025-0003.php)).

The arithmetic for budgeting is simple: one Mbit/s sustained for an hour in one direction is about 0.45 GB, so a 1.5 Mbit/s stream costs ≈0.675 GB per relayed viewer-hour one-way, and typically 10–25% of viewers need the relay ([Fora Soft](https://www.forasoft.com/learn/video-streaming/articles-streaming/turn-bandwidth-calculator); [ExpressTURN streaming](https://www.expressturn.com/streaming)). Cloudflare's free tier therefore covers roughly 1,480 relayed viewer-hours a month before the first cent, far beyond volunteer use; the real risk there is not cost but a leaked minting endpoint being driven into the paid zone, which is what the 48-hour maximum TTL and per-username revocation are for.

## Prioritized recommendations for Undepressable

### 1. Let a configured UDP TURN relay be the only STUN source

This is the highest-value change because it converts the relay the app already asks users to configure into a self-controlled replacement for every public STUN host, and it costs no new infrastructure. When a `RelaySetup` contains a `turn:` URL with `?transport=udp` (or no transport, which defaults to UDP), the app can omit `STUN_SERVERS` entirely and still receive host, server-reflexive and relay candidates in Chromium, Edge and Safari, because libwebrtc inserts every UDP TURN address into its STUN list by default, and in Firefox, whose relay candidates carry a piggybacked srflx ([basic_port_allocator.cc](https://chromium.googlesource.com/external/webrtc/+/refs/heads/main/p2p/client/basic_port_allocator.cc); [Mozilla bug 1208096](https://bugzilla.mozilla.org/show_bug.cgi?id=1208096)). Three rules make it safe. First, a relay spec must include a UDP `turn:` URL as well as `turns:…:443`; the current `parseTurnSpec` accepts any mix, so the Network page should warn when a setup is TLS-only, since such a setup produces no srflx and forces every connection through the relay even outside blend-in mode. Second, the NAT probe should use the TURN host as one of its two STUN addresses whenever a relay is configured, so the probe measures the path the app will actually use. Third, Cloudflare must be verified before the app treats it as a STUN source: Cloudflare documents Binding only on `stun.cloudflare.com`, not `turn.cloudflare.com` ([Cloudflare TURN docs](https://developers.cloudflare.com/realtime/turn/)); if the relay self-test gathers no srflx from a Cloudflare TURN entry, keep `stun.cloudflare.com:3478` alongside it. Public STUN then becomes what it should be: a fallback for users with no relay, and a mild accelerant for the rest.

### 2. Rewrite the default STUN list around port 3478 and address diversity, not port 443

Drop `stun.nextcloud.com:443`: the port-443 UDP filter in Russia (95–98% failure since July 2026) and Iran (98–100% since June 2026), the elevated failure even in Germany (14.4%), and Tor's April 2026 removal for broken NAT discovery all point the same way ([OONI RU nextcloud:443](https://api.ooni.io/api/v1/aggregation?test_name=stunreachability&probe_cc=RU&since=2025-01-01&until=2026-10-13&time_grain=month&axis_x=measurement_start_day&input=stun://stun.nextcloud.com:443); [OONI IR](https://api.ooni.io/api/v1/aggregation?test_name=stunreachability&probe_cc=IR&since=2026-04-01&until=2026-10-13&axis_x=input); [MR !1462](https://gitlab.torproject.org/tpo/applications/tor-browser-build/-/merge_requests/1462)). Drop `stun1.l.google.com:19302`, which resolves to the same address as `stun.l.google.com` and therefore only protects against a DNS failure of one name ([valid_ipv6s.txt](https://raw.githubusercontent.com/pradt2/always-online-stun/master/valid_ipv6s.txt)). Keep `stun.l.google.com:19302` for its reach outside Russia and `stun.cloudflare.com:3478` for its documented free, unlimited anycast service. Add two hosts that are in Tor's validated 2026 list, hourly-validated on UDP, and ≤2% anomalous from Russia, Iran and China: **`stun.telnyx.com:3478`** (also TCP-valid, 1.2% RU, 1% IR, 0.4% DE) and **`stun.epygi.com:3478`** (1.3% RU, 2% IR, 1.1% CN), with `stun.m-online.net:3478` (0.5% RU, 1% IR, a German operator) as the first opt-in extra ([valid_hosts_tcp.txt](https://raw.githubusercontent.com/pradt2/always-online-stun/master/valid_hosts_tcp.txt); [OONI RU](https://api.ooni.io/api/v1/aggregation?test_name=stunreachability&probe_cc=RU&since=2026-04-01&until=2026-10-13&axis_x=input)). Four defaults is the right size: js-libp2p caps at four because libwebrtc warns at five or more ([js-libp2p constants](https://github.com/libp2p/js-libp2p/blob/main/packages/transport-webrtc/src/constants.ts)). Never add `stun.voipgate.com` or `stun.mixvoip.com` despite their presence in Tor's line; they geoblock Russia and China. In `EXTRA_STUN_CANDIDATES`, `stun.t-online.de`, `stun.linphone.org` and `relay.webwormhole.io` are confirmed in the hourly UDP list, but `stun.aa.net.uk`, `stun.acrobits.cz`, `stun.gigaset.net` and `stun.frozenmountain.com` were not checked by this research and `stun3.l.google.com` likely shares Google's address; the in-app test already filters dead entries, but the fresh-list fetch from `valid_hosts.txt` should prefer port-3478 entries and could use `valid_ipv4s.txt` to sidestep DNS blocking, as the list's README suggests ([valid_hosts.txt](https://raw.githubusercontent.com/pradt2/always-online-stun/master/valid_hosts.txt); [README](https://raw.githubusercontent.com/pradt2/always-online-stun/master/README.md)). The source comment claiming 443 "survives some UDP-hostile networks" should be inverted to say that UDP/443 is now the first port censors filter, and that in Russia the STUN message itself is a DPI selector regardless of host or port, so the answer there is blend-in, not another server ([zapret #1668](https://github.com/bol-van/zapret/discussions/1668)). Because these blocks fluctuate month to month (Russia's Google figure dipped to 29% in February 2026, Iran's spiked to 75% in May), the runtime probing the app already does matters more than any static list.

### 3. Treat global IPv6 as the first direct path and say so in the Network page

The NAT probe already records whether a global IPv6 address was seen; the app should promote that to a first-class verdict — "both devices have IPv6: direct connection needs no STUN and no relay" — and never filter IPv6 host candidates. libwebrtc will try IPv6 pairs first by precedence, so nothing needs forcing ([ip_address.cc](https://chromium.googlesource.com/external/webrtc/+/refs/heads/main/rtc_base/ip_address.cc)). The expectation to set is regional: in Germany (72.9% capable) a filmer on a Telekom or Vodafone SIM talking to a German home connection has good odds; in Iceland (13%), on most VPN exits, and on IPv4-only mobile APNs the path is absent ([APNIC DE](https://data1.labs.apnic.net/v6stats/v6economy/DE.json); [APNIC IS](https://data1.labs.apnic.net/v6stats/v6economy/IS.json)). IPv6 is disproportionately valuable here because DS-Lite and CGNAT deployments hide IPv4 behind exactly the NATs that break hole punching while exposing native IPv6. Two cautions belong in the docs: a firewall that blocks outbound UDP kills IPv6 as surely as IPv4, and relay addresses from Cloudflare TURN are IPv4 only, so an IPv6-only viewer still relies on the carrier's NAT64 for the relayed path ([Cloudflare TURN FAQ](https://developers.cloudflare.com/realtime/turn/faq/)).

### 4. Ship a named relay with public, capped credentials — and remove the two unverifiable public relays

The published site should carry a relay the maintainer controls, with the credential model chosen for a static site: a long-term username and password that is public by design, protected by hard caps rather than secrecy, rotated at each deploy. The cheapest and most controllable option is a **Hetzner or OVH VPS at €4–5/month** running coturn (or eturnal) with `turns:` on 443 next to the Nostr relay, which also gives the app its own UDP STUN source for recommendation 1; its weakness is that a single IP is easy to block, so it serves Germany-to-Iceland well and hostile countries poorly. The hosted complement for hostile networks is **Metered**, whose Credential API Key and credentials link are documented as front-end safe and plug directly into the app's existing `?ice=` credentials-URL path, with quota auto-disable as the backstop; the maintainer should read the dashboard quota because the free allowance is documented three different ways ([Metered TURN REST API](https://www.metered.ca/docs/turn-rest-api/); [Metered STUN/TURN](https://www.metered.ca/stun-turn)). **Cloudflare** is the best price-performance (1,000 GB free, anycast, `turns:443`) but only if the project accepts a Worker holding the TURN token — a departure from "no backend" that should be a documented, optional deployment rather than the default ([Cloudflare pricing](https://developers.cloudflare.com/realtime/pricing/)). **ExpressTURN at $9/month** is the cheapest hosted `turns:443` with static credentials and 5 TB if a Metered quota proves too small ([ExpressTURN](https://www.expressturn.com/)). Remove `freestun.net` and `relay.backups.cz` from `PUBLIC_RELAY_CANDIDATES`, or label them "unverified since 2025": this research could not confirm that either exists as a service, and the only shared pool with a living public secret is Open Relay's `staticauth.openrelay.metered.ca` with `openrelayprojectsecret`, a 20 GB/month pool that could be offered as the opt-in "someone else's relay" candidate with an honest label ([Metered Open Relay](https://www.metered.ca/tools/openrelay/)). Whatever is chosen, the relay must advertise a UDP `turn:` URL for direct-path discovery and a `turns:…:443` URL for blend-in, and the coturn quotas (`user-quota`, `total-quota`, `max-bps`, `bps-capacity`, `denied-peer-ip`) or Metered's quota actions are what make a public credential survivable ([coturn turnserver.conf](https://raw.githubusercontent.com/coturn/coturn/master/examples/etc/turnserver.conf)).

### 5. Say plainly what only a relay solves

The documentation and the Network page should state the boundary without hedging. Two endpoint-dependent NATs with no shared IPv6 — the VPN-exit-plus-carrier case from the field test — connect only through a relay; so does any pair where either side blocks outbound UDP, since browser ICE-TCP is active-only and cannot reach another browser; so does any network whose DPI matches STUN or DTLS, as Russia's now does; and blend-in mode is relay-only by definition ([RFC 8656](https://www.rfc-editor.org/rfc/rfc8656.html); [Tailscale](https://tailscale.com/blog/how-nat-traversal-works); [net4people #603](https://github.com/net4people/bbs/issues/603)). No STUN list, no port trick and no browser feature shipped or drafted through 2026 changes this. What the app can promise instead is a precise ladder: IPv6 direct when both have it, direct via the relay-as-STUN when one side is easy, relay when neither is — with signaling over Nostr or a messenger needed in every case, because even the server-free IPv6 path still has to exchange candidates.

## Conclusion

The research reframes the question. Undepressable's STUN list was never the thing standing between a filmer in Germany and a viewer behind a VPN; a public STUN server only tells a device its own address, and the field failure belongs to the class of NAT pairs that no address knowledge can cross. The useful insight is that the app already owns the right primitive — a user-configured TURN relay — and that browsers quietly treat a UDP TURN server as a STUN server, so the "third-party STUN" dependency dissolves the moment a relay is configured, without any new infrastructure. Public STUN then shrinks to a courtesy for users with nothing configured, and for that courtesy the evidence favours Cloudflare, Google and a few Tor-vetted 3478 hosts over anything on port 443, whose supposed firewall-friendliness has turned into a liability under QUIC-style UDP filtering.

The second shift is in how to think about censorship resistance here. Snowflake's "public STUN only, no TURN" design survives because it connects to anyone; a point-to-point streaming app cannot borrow it, and every point-to-point production service has settled on an owned relay with a TLS-on-443 door. The open design question for the project is therefore not which STUN hosts to list but which relay posture to publish: a cheap self-hosted single IP that is easy to block, a hosted anycast relay whose collateral-damage protection is a plausible but untested hypothesis, or both, selected by the NAT probe. Measuring that choice in the field — which relay the Iceland–Germany pair actually connects through, and how often viewers in Russia or Iran need blend-in at all — would be worth more than any further list curation.
